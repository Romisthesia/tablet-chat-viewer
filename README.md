# 聊天记录查看器

把教育平板 / 校园 App 导出的一堆 HTML 聊天记录导入进来，按聊天软件的样子翻看。

纯前端单文件程序：不用安装、不起服务、文字部分不联网。用 Chrome 打开效果最好。仓库里自带一份**虚构的样例数据**，clone 下来就能直接跑起来和跑测试。

## 一、怎么用

双击 `chat_viewer.html`（或 `open_viewer.cmd`），然后三选一：

- **选择记录文件夹** → 选那堆导出 HTML 所在的文件夹（想先试试就选仓库里的 `sample_data/`）
- 直接把文件夹**拖进窗口**
- **导入数据包 .json** → 之前用设置里「导出数据包」生成的 `chat_data.json`，秒开

第一次导入后数据会缓存在浏览器本地，**之后每次打开自动恢复**，不用再选。

## 二、它认什么格式

教学平板类 App 导出的记录通常长这样——一个 HTML，正文里塞一个 JS 数组：

```html
<script>
var array = [{'fromId': 1002, 'sessionId': 2005, 'sessionType': 'GROUP',
              'type': 'GROUP_TEXT', 'content': '你好', 'createdTime': 1719474180803,
              'fromName': '张三', 'datetime': '2024-06-27 15:43:00'}, ...];
</script>
```

用到的字段：

| 字段 | 用途 |
|---|---|
| `sessionType` | `GROUP` / `SINGLE`，区分群聊私聊 |
| `type` | `GROUP_TEXT` / `SINGLE_TEXT` / `*_IMAGE` / `*_NOTE` / `*_AUDIO` |
| `content` | 文字消息是原文；图片/笔记是一段 JSON，里面的 `serverimg_url` 是图床地址 |
| `fromId` / `sessionId` | 私聊里 `sessionId` 就是对方的用户 id —— 靠这个自动推断「我」是谁 |
| `fromName` / `datetime` | 昵称与时间 |

界面**不需要**记录里有会话名，直接用文件名当会话名。格式不完全一样的话，改 `_parse.js` 里的 `normMsg` 即可。

## 三、功能

- 左侧会话列表（群/私标记、最后一条消息、条数），右侧气泡聊天
- 默认「我」靠右绿色气泡、别人靠左白色气泡（微信配色）
- 按天分隔；同一会话里间隔超过 5 分钟插一条时间；群聊每条显示发言人昵称
- 头像按昵称首字生成，颜色由昵称哈希决定
- 图片按原图比例显示，点开看大图、再点放大 2 倍、Esc 关闭；加载失败给占位框和原图链接
- **全部消息全文搜索**，点结果跳到那一句并在会话里高亮关键词
- 消息多时分批渲染（250 / 2000 条一批），滚到顶自动继续载入
- 主题三态：**跟随系统**（默认）/ 浅色 / 深色；跟随系统时会实时响应系统切换（右上角按钮可从自动切到显式模式）
- 跳转日期、只看占位框不加载图片
- 设置里可改「我是谁」（决定左右分布）、排序方式
- 导出数据包（备份 / 换电脑）、把单个会话导出成独立 HTML
- 设置里可「清除本地缓存」，也可关掉「记住导入的数据」（关掉后不再写入缓存）
- `Ctrl+F` 定位搜索框，`Esc` 关闭弹层

实测规模参考：我用它处理过 80 个会话 / 19 万条消息 / 2.4 万张图片（跨度 4 年），解析约 0.8 秒，打开 3 万条的会话 10 毫秒，全文搜索几毫秒。

## 四、开发时踩过的三个坑

记下来免得重复踩：

**1. 正文里的 `];` 会把文件从中间截断。**
导出文件用 `var array = [...]` 包数组，如果用 `indexOf('];')` 找结尾，只要某条消息正文里恰好出现 `];`，就会从这里切断。我遇到的两个最大文件（11.3 MB、1.3 MB）就是这样被判成语法错误，分别只解析出 0 条和 180 条，其余全丢。
解法：换成带**字符串 / 转义 / 括号深度**感知的扫描器定位真正的结尾（`_parse.js` 里的 `extractArray`），并对整段数组解析失败的情况准备逐对象容错解析兜底。`sample_data/陈屿.html` 里特意埋了一条含 `];` 的消息，作为这个 bug 的回归样本。

**2. 图片懒加载会把版面撑开。**
图片不预留尺寸时，懒加载会让内容高度不断变化，导致「跳到搜索结果」的落地位置偏掉。
解法：记录里自带 `img_width` / `img_height`，提前算出显示尺寸写进 `width` / `height`，版面稳定。

**3. 开机缓存恢复会和手动导入打架。**
查看器启动时会异步读本地缓存，如果用户这时候正好手动导入了，缓存恢复可能把刚导入的数据覆盖掉。
解法：手动导入一启动就打标记，缓存恢复完成后发现标记就直接放弃。

三条都是自动化验证（真 Chrome 驱动、`file://` 打开、断言真实 DOM）跑出来的，不是读代码看出来的——第 2、3 条尤其。

## 五、隐私

这个工具是**本地纯前端**的：数据不经过任何服务器，不上传、不联网（除了按需去图床拉图片）。

但导出文件和它的副本（数据包、测试截图）里就是真实的聊天内容，所以：

- `.gitignore` 已经挡住 `chat_data*.json`、`dev/screenshots/`、`*.png`
- 仓库里带的 `sample_data/` 是脚本生成的虚构数据，可以放心提交
- `dev/check_privacy.sh` 可以自查：扫工作区 + **每个 git 引用的历史** + 悬空对象

```bash
PATTERNS="你的名字|你的ID|你的机器名" bash dev/check_privacy.sh
```

**一条踩过的坑（值得单独说）**：`git commit --amend` 和 `rebase` 只是把分支指针挪到新提交，**旧提交仍然留在 `.git` 里**；只要旧提交还在某个引用的祖先链上（比如它是当前分支的父提交），`git push` 就会把它连着一起传上去。我就是这样把一份脱敏前的提交推到了远端——因为当时只检查了 tip 提交的内容，没检查它的祖先。正确做法是脱敏后**压平历史**（`git checkout --orphan` 重建一个干净的根提交），再 `git reflog expire --expire=now --all && git gc --prune=now`，最后用上面的脚本复查每个引用。
- **用自己的真实数据跑测试时，建议把输出指到项目外**，避免真实数据落在仓库目录里：

```bash
CHAT_DIR="/path/to/真实记录" \
SHOT_DIR="/tmp/shots" \
PKG_OUT="/tmp/chat_data.json" \
npm test
```

（`CHAT_DIR` 是只读输入，不会改动你的原始记录。）

### 关于本地缓存（实测过）

为了「下次打开自动恢复、不用重选文件夹」，查看器会把导入结果缓存在浏览器的 IndexedDB 里（数据库名固定为 `chatviewer`，只用一个槽位，所以后导入的会覆盖先前的）。两个实测结论：

- **缓存按浏览器隔离，跟文件路径无关。** 实测：在主程序原路径导入后，把 `chat_viewer.html` 复制到另一个完全不同的目录，用同一个浏览器打开，**照样自动载入了同一份记录**。原因是 Chrome 把所有 `file://` 页面视为同一个来源，共享同一份存储。换一个浏览器（或全新用户目录）则读不到，会停在导入页。
- **所有本地 HTML 共享这份存储**，所以任何你双击打开的本地网页，理论上都能读到这个 `chatviewer` 数据库。实测：一个和本项目无关的本地 HTML 确实读出了缓存的字节数。

想清掉：设置里点「清除本地缓存」（会先弹确认框），或在控制台执行 `indexedDB.deleteDatabase('chatviewer')`；也可以关掉「记住导入的数据」，之后不再写入。想彻底不留痕，用无痕窗口打开即可。

## 六、目录结构

```
chat_viewer.html     查看器本体（单文件，可单独拷走）
open_viewer.cmd      双击打开
sample_data/         虚构样例数据（3 个会话 / 41 条，脚本生成，含回归样本）
package.json         根目录命令入口，转发到 dev/
.gitignore
dev/                 开发与验证脚本
├── _config.js       路径与 Chrome 探测（全部可用环境变量覆盖）
├── _parse.js        解析器（node 版，与页面里那份逻辑一致）
├── _count.js        统计：会话/消息/类型/发言人/「我」是谁
├── make_sample.js   生成 sample_data/
├── check_privacy.sh 隐私自查：工作区 + 各引用历史 + 悬空对象
├── _build_pkg.js    生成数据包
├── _verify_parse.js 解析一致性：浏览器结果 vs node 逐会话对比
├── _verify_ui.js    界面：布局几何、配色、图片、灯箱、搜索跳转、深色模式
├── _verify_pkg.js   数据包导入往返 + 重开自动恢复
└── _verify_full.js  全量压测：解析耗时、内存、大会话切换、分批渲染
```

## 七、跑验证

在项目根目录：

```bash
npm install --prefix dev    # 只装验证用的 puppeteer-core
npm test                    # 用自带的虚构样例数据：解析一致性 + 界面 + 数据包
```

换成自己的真实记录（推荐把输出指到项目外）：

```bash
CHAT_DIR="/path/to/你的导出目录" npm test
CHAT_DIR="..." npm run test:full   # 全量压测
CHAT_DIR="..." npm run stats       # 统计这批记录
CHAT_DIR="..." npm run build       # 生成 chat_data.json
npm run sample                     # 重新生成样例数据
```

Windows PowerShell 里设环境变量：`$env:CHAT_DIR="D:\records"; npm test`

验证方式是用 `puppeteer-core` 驱动本机 Chrome、以 `file://` 打开查看器（与双击完全同路径），断言真实 DOM 与几何数值，不是看代码猜。样例数据不含图片，相关检查会自动跳过并打印说明。

## 八、已知限制

- 图片是**在线**从原平台图床加载的，断网或图床清了文件就只剩占位框（会提示并给原图链接）。文字部分完全离线。
- 只对「`var array = [...]` + 上述字段」这种导出格式有效；其它格式要自己改 `normMsg`。
- 语音消息的分支保留了，但没有真实语音样本可测。
